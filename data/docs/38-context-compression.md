# 上下文压缩与对话记忆

## 多轮对话的预算是有限的

每一轮对话都要把历史重新发给模型，因此成本随轮次累积增长，
而且增长速度比直觉更快：第二轮发一份历史，第三轮发两份，
第 n 轮的输入长度是前 n 减一轮的总和。

即使单轮内容不长，到十几轮之后输入长度也会超出预算。
因此多轮场景必须有压缩策略，不能依赖"上下文足够大"。

## 三种压缩方式的取舍

**滑动窗口**只保留最近若干轮。实现最简单，
代价是丢失早期的关键信息，用户会感觉系统"忘了"之前说过的约束。

**摘要**把早期对话压成一段概述。它保留了语义，
但摘要是有损的，而且摘要本身由模型生成，
会引入误差。关键约束如果在摘要里被弱化，
后面几轮的行为就会漂移。

**关键信息抽取**把对话里的事实性内容抽成结构化字段，
比如用户的身份、目标、已经排除的选项。它最精确，
但需要先定义要抽取什么，对开放对话的适应性差。

实用的组合是按时间分层：最近几轮保留原文，
更早的部分用摘要，再早的部分只保留抽取出来的关键字段。

## 摘要要保留什么

摘要最容易被写坏的地方是把它写成"对话讲了什么"的复述。
复述对后续对话没有帮助，因为模型需要的是约束条件而不是情节。

有用的摘要包含三类内容：用户明确提出的要求、
已经确认的结论、以及被排除的选项。
第三类最容易被漏掉，但正是它防止模型反复推荐用户已经否决过的方案。

摘要还应当保留**未解决的问题**。多轮对话里经常出现
用户提了三个问题但只回答了前两个的情况，
如果摘要只记录已答内容，第三个问题会在压缩之后彻底消失。

## 压缩触发时机

触发压缩的时机有两种：按轮次触发和按长度触发。
按轮次更可预期，按长度更节省。

更值得关注的是触发后的行为。压缩是一次额外的模型调用，
它会增加当轮的延迟。因此压缩不适合在用户提问的那一轮同步执行，
否则用户会明显感到每若干轮就有一次卡顿。

可行的做法是异步压缩：在后台提前把已经稳定的历史压好，
下一轮直接使用压缩结果。

## 压缩会掩盖问题

压缩引入了一个新的失败模式：压缩之后系统答错了，
但从当前上下文里看不出原因，因为关键信息在压缩阶段被丢掉了。

因此每次压缩都要保留原始历史与压缩结果的对应记录，
并且在评测集里加入**跨轮记忆**的样本：
先建立约束，隔若干轮之后提问，检查约束是否仍然生效。

没有这类样本，压缩策略的退化是无声的。
