# 模型网关与配额

## 一次请求的编排顺序

网关处理一次对话请求的顺序是固定的：配额扣减、语义缓存查询、路由选档、调用上游、
必要时级联升级、异步落账。顺序不能随意调整，每一步都有理由。

配额必须放在最前面。如果先查缓存再扣配额，缓存命中也会消耗额度，
而缓存命中实际上没有产生任何上游成本，这会让计费口径和真实成本脱节。

## 配额是怎么做到不超发的

配额扣减依赖 Redis 与 Lua 脚本。关键在于把“读取当前用量、判断是否超额、写回新用量”
三步放进同一个 Lua 脚本。Redis 执行脚本时是单线程的，脚本内部不会被打断，
因此这三步对外表现为一个原子操作。

如果用普通的读改写，两个并发请求可能同时读到剩余额度充足，然后各自扣减，
最终超额放行。压测场景下用 60 个并发打同一个租户，正确实现的表现是恰好 30 个放行、
30 个被拒，且账本记录的用量恰好等于额度上限。

## 上游不可用时怎么办

配额判断依赖 Redis。如果 Redis 不可用，网关选择放行而不是拒绝。
理由是可观测性系统不应该成为业务的单点故障：额度暂时算不准是可以接受的，
把全部业务请求因为这个组件而拒绝掉是不可接受的。

这个选择的前提是配额本身是成本控制手段，不是安全边界。如果它是安全边界，
就必须改成失败时拒绝。

## 成本核算

账本按输入 token 与输出 token 分别计价。两者单价通常相差数倍，
合并成一个总数再乘平均价会系统性低估长输出的成本。

每一次真实发生的上游调用都必须单独落一条账，包括被路由升级掉的那一次。
级联升级场景下实际上发生了两次调用、产生了两次费用，只记最终那一次会让成本归因偏低。

## 写账本为什么不能同步做

账本写入曾经是响应路径上的同步调用，压测时发现每个请求会多花几十秒。
根因是消息队列客户端在 broker 不可达时会阻塞到最大阻塞时间才抛超时异常。
修复方式是两件事同时做：把最大阻塞时间压到几百毫秒，并把落账丢到独立线程异步执行。

只做其中一件都不够。只调小超时仍然会在响应路径上等；只改异步则单次调用仍可能长时间卡住工作线程。
