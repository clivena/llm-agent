# 提示词工程与版本管理

## 提示词是代码

提示词一旦上线就会影响效果，但它经常被当作配置文件随手改动，
既没有版本，也没有回归。正确做法是把提示词按版本落成独立文件，
进入代码评审，并在改动后跑同一批样例做对比。

版本文件必须能被追溯到具体运行。评测结果里要记录用的是哪个版本，
否则数字对不上时无法判断是模型变了还是提示词变了。

## 结构化输出

要求模型输出结构化内容时，有两个策略：一是明确要求只输出 JSON，
二是在提示里给出字段说明与示例。

实测中只加约束不加示例，通过率会下降。原因不是模型不会，而是它对字段命名、
嵌套层级、空值表示有大量自由发挥空间，评测集无法穷举这些变化。

## 温度与确定性

需要可复现的评测时，温度应当设得足够低。温度高会让同一提示词产生不同输出，
这本身不是问题，但它会让"这次和上次分数不一样"变成一个无法归因的现象。

低温度不能保证完全确定，因此评测仍需多次采样并报告方差，
而不是把一次结果当成稳定结论。

## 常见反模式

把业务逻辑写进提示词是最常见的反模式。判断分支、格式转换、字段映射
这些有确定答案的事情应该由代码做，交给模型只会引入不确定性且更难测试。

另一个反模式是把提示词写得越来越长来修补个例。每修一个个例就加一句约束，
最终提示词会变得互相冲突，且没有任何一条能被验证。
正确做法是把个例变成评测集里的一个用例。
