# 流式响应的错误处理

## 首字节之后错误就不可撤销

流式接口的响应一旦开始，客户端可能已经渲染了部分内容。
此时上游出错，能做的选择只有三个：
中断连接并标记为不完整、继续发送剩下的内容、
或者发送一个结构化的错误事件让客户端决定如何处理。

最差的做法是静默截断。客户端收到的流正常结束，
但内容是半句话，而错误码是成功的。这种情况在客户端看来
和"模型本来就答得短"完全无法区分，问题会被长期隐藏。

因此流式协议必须有一个明确的结束语义：
正常结束有结束标记，异常结束有错误事件，
两者必须互斥且必居其一。

## 分块边界与内容完整性

流式传输会把文本切成分块，切点通常在词元边界上，
因此单个分块可能只有一两个字，甚至是半个多字节字符。

客户端拼装时最容易犯的错误是按分块做处理，
比如对每个分块做一次 JSON 解析。正确做法是缓冲到完整的结构再处理。

服务端侧则要注意不要为了"凑成一个完整句子"而引入额外延迟。
分块的粒度会影响体感：按很小的粒度推送，
用户看到的是逐字出现；按句子推送，首字节延迟更低但初始体验是空白。
这个取舍取决于场景，但必须在实现里显式选择，而不是由缓冲区的默认行为决定。

## 背压

流式响应里生产者是模型，消费者是客户端。
如果客户端读取速度跟不上生成速度，数据会在中间的缓冲区里堆积。

在没有背压机制的实现里，堆积的结果是内存增长，
最终在负载高的时候表现为内存溢出。
更隐蔽的是它不会立刻失败，而是在流量高峰才出现，
排查时容易被误判为内存泄漏。

处理方式是在每一层设置缓冲区上限，
超出上限时选择阻塞生成或者丢弃并记录。
对生成类接口来说，阻塞生成通常更合适，
因为丢弃的内容无法恢复。

## 重试与断点续传

流式请求的重试只能发生在首字节之前。
一旦开始输出，重试会产生两段拼接内容，
语义上无法接受。

如果确实需要支持中断后的恢复，正确做法是
把生成与传输解耦：生成完成后落到存储，
客户端通过一个独立的接口按偏移量拉取。
这样断线之后可以从上次的位置继续，
代价是失去了"边生成边看"的体验。

因此断点续传和实时流式在架构上是互斥的，
需要按场景选择，不能同时要求两者。

## 超时要分层设置

流式请求至少有三层超时：建立连接的超时、
首字节到达的超时、以及两个分块之间的间隔超时。

只设一个总超时是不够的：一个总时长十分钟的请求，
可能是正常的长时间生成，也可能是已经卡死但恰好没到总超时。
分层超时能更早地识别卡死，同时不误杀正常的长生成。
