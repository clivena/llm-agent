# 结构化输出与校验

## 为什么要约束输出格式

把模型输出当作程序输入使用的时候，格式就是接口。
模型偶尔多说一句解释、偶尔把字段名写成中文、偶尔在 JSON 外面包一层代码块标记，
上游都会解析失败。而且这种失败是间歇性的，
在测试环境不容易复现，到了线上就成了稳定的报错来源。

约束输出格式的目标不是让输出好看，而是让**解析失败可被发现、可被拦截**。

## 三种约束手段的强度不同

最弱的是在提示词里写清楚要求和示例。它有效但不可靠，
模型在长上下文或者复杂任务下会逐渐忽略格式要求。

中等强度的是要求模型调用一个带参数定义的函数，
由模型服务端负责生成符合参数结构的内容。它对结构有强制力，
但字段取值仍然自由。

最强的是在模型侧开启受约束的解码，从采样阶段就禁止输出不符合语法的词元。
它的结构正确率最高，代价是会稍微影响生成质量，
因为模型被剥夺了"先想一想再回答"的余地。

实用的组合是：用函数调用约束结构，用校验层约束取值，
并对校验失败做一次带错误信息的重试。

## 校验要分层

校验不能只做语法层。一条通过的 JSON 可能字段齐全但取值荒谬：
日期是未来时间、分数是负数、枚举值不在允许范围内、
引用的块编号在索引里根本不存在。

因此校验至少要分三层：语法可解析、结构符合模式、**语义上可引用**。
第三层最容易被忽略也最重要。如果输出里带着引用编号，
那么校验必须确认每个编号都能对应到真实的语料片段，
否则引用就是装饰品。

## 失败之后的处理

校验失败有两种处理方式，选哪种取决于失败的原因是否已知。

如果是模型偶尔的格式漂移，带上具体的校验错误信息重试一次，
通常就能通过。错误信息要具体到哪个字段、期望什么、实际是什么，
只说"格式错误"对模型没有帮助。

如果同一批输入反复失败同一处，说明提示词或者模式定义本身有问题，
这时重试是在浪费钱。正确的做法是把失败样本记录下来，
作为提示词迭代的输入，并在统计上把这类失败单独计数——
它和模型能力不足是不同的失败模式，混在一起看会掩盖真正的问题。

## 校验结果要进入指标

把校验通过率作为一个独立的指标记录下来，而不是并入准确率。
原因是这两者的变化趋势经常相反：为了让模型更好地理解任务而放宽格式要求，
准确率可能上升、校验通过率下降；反过来收紧约束会提高通过率但压低质量。

只有把两个指标分开看，才能找到二者都好的那个平衡点。
