# agentkit —— 可溯源的检索增强智能体

一个能**离线跑通、每个数字都能自查**的 RAG + 工具调用 Agent。
不是 demo 拼装：切块、召回、重排、引用溯源、工具容错、成本统计，每一环都有对应的
设计取舍说明、单元测试和可复现的评测数字。

```
文档 → 切块 → 向量化 → 召回 → 重排 → 上下文组装
                                        ↓
                           ┌── ReAct 循环 ──┐
                           │  调工具 / 作答  │
                           └────────────────┘
                                        ↓
                                 答案 + 引用 + 轨迹 + 成本
```

## 30 秒跑起来

```bash
pip install -e ".[dev]"

agentkit ingest                       # 把 data/docs 切片入库（离线，零成本）
agentkit ask "工具执行失败会不会中断整轮问答？"
agentkit eval                         # 检索质量：重排前 vs 重排后
agentkit bench --backends stub,direct # 跨后端对比调用次数 / token / 成本 / 缓存命中
agentkit serve                        # 浏览器里现场演示
```

`ingest` 到 `ask` 之间不需要任何 API Key、不需要网络。

不想操心解释器和相对路径，直接用脚本：

```bash
scripts/start-console.cmd                   # 起 8765 演示控制台（stub，离线、零成本）
scripts/start-console.cmd --backend direct  # 连真实模型
scripts/start-console.cmd --backend gateway --port 9000
```

脚本会自己解决三件事：

1. **找一个真的装齐本仓依赖的解释器** —— 它逐个 `import` 试（typer / rich / pydantic），
   所以 PATH 上排最前的那个"干净"托管解释器会被自动跳过。要指定就用 `AGENTKIT_PYTHON`。
2. **切到仓根目录再起** —— `index_path` 是相对路径 `out/index.jsonl`，在别处启动会解析不到索引。
3. **把静态失败挡在启动之前** —— 索引不在就先 `ingest`；`--backend direct` 缺 `AGENTKIT_API_KEY`、
   或 `--backend gateway` 缺 `AGENTKIT_CHAT_MODEL` 时直接报错退出，而不是起好之后再 502。

> 脚本文件保持**纯 ASCII**：cmd.exe 按控制台代码页（中文 Windows 是 GBK）解析 `.cmd`，
> UTF-8 的中文注释会被错误解码、吃掉换行，脚本会以一堆 `'cho' 不是内部或外部命令` 崩掉。
> 中文说明放 README，不放 `.cmd`。

## 它解决什么问题

**问题：RAG 项目最难的不是"接上大模型"，而是"证明它没在胡说"。**

多数 RAG 演示止步于"能返回一段看起来相关的文本"。这个项目把三件通常被跳过的事做实了：

| 通常的做法 | 这里的做法 |
|---|---|
| 引用只写"来自某文档" | 引用带**字符区间**，可以拿回原文精确落位、逐条强校验 |
| 检索质量靠"感觉还行" | 同一批检索结果做重排前后对照，输出 recall@k / MRR / hit_rate |
| 成本统计只记最后一次调用 | 一次问答的**全部**调用（规划 + 重排 + 摘要）合并记账 |

## 三个后端，一套代码

同一个 `OpenAiCompatibleClient` 服务两种联网后端，差别只有 `base_url` 与鉴权头：

| 后端 | 用途 | 需要的凭据 |
|---|---|---|
| `stub` | 全离线。跑同一个 ReAct 循环、同一套提示词，只是决策者换成一个确定的、很笨的模型 | 无 |
| `direct` | 直连任意 OpenAI 兼容端点（厂商 API / vLLM / Ollama） | API Key |
| `gateway` | 指向同族的自研网关 `llm-gateway`，配额 / 语义缓存 / 成本账本 / traceId 全链路贯通 | 网关 key |

之所以能做到"一套代码"，是因为网关补齐了**响应侧**的 OpenAI 兼容性
（`choices[].message.content`、snake_case usage、`[DONE]` 终止帧、`/v1/embeddings`）。
补齐之前网关只兼容请求侧，客户端必须写两套解析，"可切换后端"就只是口号。

`stub` 不是 mock：`StubClient` 解析的是**真实提示词里的标记**，
所以离线跑出来的 trace、引用、检索指标，和联网跑出来的形状完全一致。
它的存在是为了让效果验证有一个稳定基线，也让演示不依赖网络。

## 效果数字（离线基线，`agentkit eval`）

语料：45 篇中文文档 / 216 个切片；评测集：134 条查询，
按"来源文件 + 段落关键词"判定相关性（避免文件级判定被段落级差异掩盖）。

| 排序策略 | recall@4 | MRR | hit_rate | n |
|---|---|---|---|---|
| recall-only（纯余弦） | 0.8731 | 0.7811 | 87.31% | 134 |
| rerank（启发式融合） | **0.9179** | **0.8414** | **91.79%** | 134 |

k 扫描：重排在 **k=1** 把 recall 从 0.7164 提到 0.7836、
**k=2** 从 0.7985 提到 0.8657、**k=3** 从 0.8582 提到 0.9104、
**k=4** 从 0.8731 提到 0.9179 —— 相对"不重排"基线，每个 k 都不劣。
（`pytest` 里有一条回归红线 `test_rerank_never_loses_to_recall_only` 守着这一点。）

权重也是扫出来的（`python scripts/tune_rerank.py`），不是拍出来的：

| 语义 : 词法 | k=1 MRR | k=2 recall | k=3 recall | k=4 MRR |
|---|---|---|---|---|
| 0 : 1（只用词法） | 0.7313 | **0.8806** | 0.9104 | 0.8197 |
| 1 : 0（等于不重排） | 0.7164 | 0.7985 | 0.8582 | 0.7811 |
| 0.45 : 0.55 | 0.7537 | 0.8582 | 0.8881 | 0.8178 |
| **0.30 : 0.70（默认）** | **0.7836** | 0.8657 | **0.9104** | **0.8414** |

两个信号各自都有短板：只用词法把权重全押在字面重合上，语义相近但换了说法的查询会掉；
只用语义等于不做重排。**融合（默认 0.30 : 0.70）在 MRR 上 4 个 k 全部高于两者**，
相对"不重排"基线每个 k 都更高 —— 这才是重排值得存在的理由。

但要如实说一句反直觉的：**纯词法在 recall@2 / recall@4 上反而最高**（0.8806 / 0.9254）。
`recall@k` 只问"答案在不在前 k 条"，MRR 还问"排在第几位"—— 重排改的正是位次。
用 MRR 衡量重排、用 recall 衡量召回，各用各的尺子，两组数字才不互相矛盾。

## 检索的天花板在切块，不在重排

`python scripts/ablation_chunking.py` 把两项切块改动做成 2×2 消融
（`A` = 硬折行归一化，`B` = 章节作为硬边界），跑的是同一套 eval：

| A 归一化 | B 章节边界 | 块数 | k=4 recall | k=4 MRR | k=1 recall |
|---|---|---|---|---|---|
| 是 | 是 | 216 | 0.8731 | **0.7811** | **0.7164** |
| 是 | 否 | 182 | 0.8731 | 0.7419 | 0.6567 |
| 否 | 是 | 217 | 0.8731 | **0.7811** | **0.7164** |
| 否 | 否 | 178 | 0.8507 | 0.7046 | 0.5970 |

结论有两层，第二层比第一层重要：

1. **章节边界仍然是主要收益来源**：k=4 的 MRR 从 0.7046 升到 0.7811（+7.7pt），
   k=1 的 recall 从 0.5970 升到 0.7164（+11.9pt）。块横跨两三个话题时，
   向量被平均掉，最相关的那一段反而排不到前面。
   （表里的指标都是 recall-only —— 消融比的是切块，不该把重排的影响混进来。）
2. **归一化在这个语料上仍然测不出指标差异**（0.7811 / 0.7164 两行完全相同），
   只是块数从 216 变成 217 —— 因为所有章节都短于 320 字的窗口，
   一个章节刚好一块，折行不影响块边界。它真正起作用的地方是"章节长于窗口"时的
   块起点，以及引用片段的显示文本。如实写下来比假装它也有收益更有价值。

## 质量门禁（CI）

`.github/workflows/agent-gate.yml` 在 PR 上跑两件事：

1. `pytest -q` —— 143 个离线用例；
2. `python scripts/quality_gate.py` —— 把检索指标变成**退出码**。

门禁里有两条硬约束，是别的地方很难替代的：

- `recall@4 ≥ 0.90`、`MRR ≥ 0.80` —— 召回质量不能悄悄退化；
- **重排的 recall 与 MRR 都不得低于 recall-only** —— 重排不能是负收益。

没有第二条，调参把指标调坏了只能靠人肉比对报表发现；
有了它，"重排退化"会直接让 CI 变红。

## 七个踩坑记录（都写进了代码注释和测试）

1. **切块横跨章节** → 向量把两三个话题平均掉。消融实验（上表）显示，
   把它改成"章节是硬边界、只在章节内部滑窗"后，召回侧 MRR 从 0.7046 升到 0.7811（+7.7pt）。
   这一步的收益比后面所有重排调参加起来都大（重排把 MRR 从 0.7811 提到 0.8414，+6.0pt）。
2. **硬折行没还原** → markdown 在句中折行会被当成段落边界，切出以半句开头的块，
   答案里出现"而不是继续使用未重排的结果冒充已完成"这种没头没尾的开头。
   在本语料上它对指标无影响（见上表），但换成长章节的语料就会暴露。
3. **切块循环不前进** → 章节尾部空白没裁掉，`end >= seg_end` 永远不成立，
   每次只前进 1~2 个字符，跑出 178 个碎片块。现在有 `test_chunk_text_terminates_on_fragmented_input` 守着。
4. **重排覆盖了召回** → 直接用词法分重排等于扔掉语义分，修好一个查询就弄坏另一个。
   改成加权融合后 MRR 才稳定为正。
5. **用量统计绑错实例** → 把 `self._stats.add` 注册成监听器，每次问答都报"调用 0 次"。
6. **环境代理劫持回环地址** → `HTTP_PROXY` 被套到 `127.0.0.1` 上，
   "连本地网关"变成"走代理再打回本机"。传输层显式装空 `ProxyHandler`。
7. **启动脚本的依赖探测比依赖本身更严** → `start-console.cmd` 的候选探测要求
   解释器能 `import typer, rich, pydantic, httpx, yaml, jinja2`，但本仓只声明
   pydantic / typer / rich，网络层用的是标准库 urllib。于是**一个按 pyproject
   正确装好的环境会被判成"不可用"**，所有候选都不通过时脚本以退出码 2 结束 ——
   README 首页那条"30 秒跑起来"的路径，在干净机器上第一步就断。
   根因是这份清单从 evalkit 的 `run-eval.cmd` 抄来（那边这 6 个包恰好都对），
   抄的时候没跟着删。教训：探测清单必须与 `pyproject.toml` 的 `dependencies`
   一一对应，"宁多勿少"会把可用环境挡在门外。

## 已知边界（不做隐瞒）

- **暴力检索**：`VectorStore.search` 是 O(n) 全扫描，没有倒排或量化索引。
  数千块以内延迟在毫秒级；再往上应该换掉 `VectorStore` 这一个类，接口不变。
- **语料扩容后指标会回落，这是真实的、也是预期的**：15 篇 / 21 条查询时 recall@4 是
  0.9524、MRR 0.9206；扩到 45 篇 / 134 条后是 0.9179 / 0.8414。
  查询变多、覆盖话题变广，小样本下"碰巧都排得准"的乐观值必然回落 ——
  这不是退化，是基线变得诚实了。代价是门禁余量收窄（MRR 距 0.80 只剩 0.041），
  后续任何改动都要更小心；README 里所有指标都带 n，就是为了让这个变化可见。
- **离线向量没有语义泛化能力**：哈希向量靠字面重合，
  "本地为什么连不上自己的服务"这类**换了说法**的问题，离线基线只能把它排到第 2 位。
  这正是换成真实 embedding 后要改进的基线 —— 数字本身也是产物。
- **LLM 重排未在离线语料上量化**：`LlmReranker` 的降级路径有完整测试（条数不符 / JSON 非法 /
  分数越界），但没有 API Key 就没法给出它的效果数字，不做推测。
- **多租户只是预留**：`tenant` 字段已贯穿配置与网关请求头，但本仓库不做鉴权与隔离。

## 相关仓库

- [llm-gateway](https://github.com/clivena/llm-gateway) —— 访问层：配额（Lua 原子扣减）、语义缓存、路由选档、成本账本、traceId
- [llm-eval](https://github.com/clivena/llm-eval) —— 质量层：规则打分、语义打分、裁判校准、回归卡关
- [llm-dashboard](https://github.com/clivena/llm-dashboard) —— 展示层：配额与成本看板、请求链路演示、
  评测结果面板（检索快照由本仓 `scripts/export-retrieval.py` 产出）
- **agentkit（本仓库）** —— 应用层：把上面两层的能力用起来

四层各自可独立运行，合起来是一条完整的"接入 → 质量 → 应用 → 可视"闭环。
`gateway` 后端就是这条闭环的接线口：Agent 复用网关的配额、缓存与账本，
`X-Cache-Hit` / `X-Trace-Id` 直接落进 `UsageStats`，
所以"这次回答有没有命中缓存、花了多少、traceId 是什么"在一张表里能看到。

## 测试

```bash
pytest -q      # 143 passed
```

全部用例不依赖网络与外部服务，也不读取仓库里的 `out/` 索引。
其中最有价值的一条是 `test_rerank_never_loses_to_recall_only`：
它在 k=1..4 上断言重排的 recall 与 MRR 都不劣于 recall-only ——
这条断言把"重排有没有用"从主观判断变成了回归红线。
